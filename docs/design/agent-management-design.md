## Problem Statement / 重新定位

原「数字员工」升级为更根本的目标：**让内核从「单 agent」变成「支持多 agent」（agent 管理）**。数字员工不再是产品本身，而是多 agent 能力落地后的**第一个应用**——一个自主/定时运行的 agent。

当前内核有三处硬约束（前几轮分析过），本设计要拆的是**最关键的第一处**：

| 约束 | 代码位置 | 本设计如何处理 |
|------|---------|---------------|
| **只有一个 agent 槽** | `AgentHolder.agent`（单 volatile 引用） | **换成 `AgentRegistry`（Map<agentId, AgentInstance>）** ← 本设计核心 |
| 只有一个活会话 | `SessionManager.currentSessionId` | 沿用；每 agent 实例各自会话，交互型仍单活 |
| `.block()` 串行 | `PigAgent.call()` | 交互型不动；自主/并发运行时按需去阻塞（阶段 2/3） |

本轮三个明确调整：
1. 概念：「数字员工」→「**Agent 管理（多 agent 内核）**」。
2. agent 结构要能**各自选模型**。
3. 多 agent 完成后接 **Web 可视化**（CLI + Web，未来还会加更多入口）→ 需要一个**前端适配层**。

## What Makes This Cool

- **一个内核，多种入口，多个 agent**：你能同时养一批 agent（各有各的模型、工具、权限、人格），在 CLI 里切换用，也能让某些 agent 自主定时跑（数字员工），未来还能在 Web 里可视化地管它们。
- **和 Claude Code 的差别**：Claude Code 的 subagent 是临时的、藏在会话里的；这里的 agent 是**一等公民**——可命名、可持久化、可各自选模型、可自主运行、可被多个前端管理。
- **守住简单**：多 agent 全部**进程内 + 文件持久化**，一行 DB / 一个消息队列都不引入。

## Constraints

- **仍面向个人电脑**：不引入 DB / 缓存 / 消息中间件 / 多租户 / 服务端集群。多 agent 是**进程内**的，文件持久化。Web server 是**嵌入式、单用户、无 DB**。
- **单 agent / 现有 CLI 路径全程不断**：多 agent「长出来」而非重写。现有那个 agent = 注册表里的 active 实例。
- **小团队慢做**：严格分层，每层独立可落地、独立产生价值。

## Premises

1. **多 agent = 进程内管理并运行多个 agent 实例**（各自 spec + 模型 + 会话 + 权限），不是分布式/多租户平台。
2. **agent 是声明式的**：`AgentSpec`（含**模型选择**）可持久化、可版本化、可分享。
3. **前端适配层**：内核暴露一个 `AgentKernel` 门面 + 事件流；CLI / Web / 未来入口都是它的 adapter，「加入口」= 加 adapter，不动内核。
4. **数字员工 = 带 schedule 的 agent** 在受限权限下自主运行并产报告；是多 agent 内核的第一个应用，不是独立子系统。
5. 仍不碰 DB/服务端；无人值守安全沿用现有权限体系（`ask` 无 confirmer → fail-closed）。

## 目标架构（分层）

```
┌ 接入/适配层 ─ CLI(REPL) │ Web(独立后续 spec) │ Channel │ 未来入口 ───────┐
│                                                                        │
│   AgentKernel（门面 API + 事件流 Flux<KernelEvent>）← 前端只依赖它       │
├ 运行层 ─ AgentRunner：交互运行（前端驱动） / 自主·定时运行（= 数字员工）   │
│           无人值守权限档 + 晨报 + 超时/中断 + 防重入                      │
├ 管理层 ─ AgentRegistry：Map<agentId, AgentInstance>（替换单 AgentHolder） │
├ 定义层 ─ AgentSpec：name + sysPrompt/mandate + toolNames + 权限          │
│           + **modelId** + 可选 schedule                                 │
└ 基座 ─ ReActAgent · Toolkit · Hook · Model · ModelStore/ModelManager      │
         · ProtocolRegistry · TaskScheduler · 权限 sentinel ──────────────┘
```

## 核心抽象

### 1. `AgentSpec`（不可变 record，`withXxx` 拷贝）—— 定义层
```
AgentSpec(
  id,                 // 短 id
  name,               // "代码守夜人" / "写作搭子"
  sysPrompt,          // 人格/系统提示（交互型用）
  mandate,            // 自主型的岗位说明（自主运行时当 user message，= 可选，交互型可空）
  toolNames,          // 工具名白名单（如 [readFile, executeCommand]）
  commandAllowlist,   // EXEC 首 token 白名单（如 [mvn, git]），复用 permissions.allowlist.commands 语义
  permissionMode,     // 权限档（plan/ask/auto/bypass）；自主型默认 auto
  modelId,            // ★ 每 agent 选模型：指向 StoredModel.id；null = 用默认模型
  maxIters,           // 运行上限
  timeoutSeconds,     // 自主运行硬超时
  schedule,           // 可选 TaskSchedule（ONCE/CRON/DELAYED）；null = 交互型/手动
  enabled,
  lastRunAt
)
```
- **模型选择（本轮 point 2）**：`modelId` → 用现有 `ModelStore` 取 `StoredModel` → 经 `ProtocolRegistry` 建 `Model`（与 onboarding / `/model` 同一条解析链）。`null` 回落默认模型；**引用的 `modelId` 对应 `StoredModel` 被删除时也容错回落默认**（仿现有 fault-tolerant 范式）。
- **权限档 per-agent**：`ToolPermissionHook` 现从全局 config 读 mode，per-agent 后须改为从 `spec.permissionMode` 读——阶段 1 一并改。
- 持久化：`workspace/agents/{id}.md` = **YAML front-matter（Jackson YAML 序列化）+ Markdown 正文（= sysPrompt 或 mandate）**。只借 `FileSystemTaskRepository` 的**容错范式**（坏文件跳过/备份、不崩列表），**不抄它丢字段的 `parseMarkdown`**。

### 2. `AgentInstance`（运行时）—— 泛化今天的 `AgentHolder.get()`
一个活 agent：`agentId + 源 AgentSpec + 内部 PigAgent + 生命周期状态（IDLE/RUNNING/…）+ 自己的会话/记忆`。

### 3. `AgentRegistry`（管理层）—— 替换单 `AgentHolder` ★本设计核心
- 持有 `Map<agentId, AgentInstance>`。交互「当前 agent」= active 实例。
- **AgentHolder 的完整读/写点（进 spec 前必须先摸清）**：
  - **只读** `agentHolder.get()` 的：`AgentRepl` / `ReplContext.agent()`、`SessionManager`、`ChannelAgentBridge`、`CompressionService`、`ReplCommands` —— 这些保留 `AgentHolder` 作「active 实例视图」即可**零变化**。
  - **写** `agentHolder.set()` 的只有一个：**`ModelManager`**——而且它**持有两个 holder（主 `holder` + `channelHolder`），`ensureModel` 里对二者都 set**。它是承重墙里真正要动的地方（不是"基座复用"）。多 agent 后它的职责要重定义：从「切唯一 agent 的模型」→「切 **active 实例**的模型（或整体交给 AgentRegistry，ModelManager 只管建 `Model`）」。
  - **channel 用独立的 `channelAgentHolder`**（自己的 agent + channel-mode 权限 hook）：门面要明确 channel 归属哪个 agent 实例。
- **不能直接复用现有 `AgentFactory`**：它的 name/sysPrompt/**toolkit/hooks/memory 都是构造时固定的全局单例**。per-agent 要各自的 toolkit 子集、权限档、记忆 → 建实例时须**仿 AgentFactory 但每 agent 新建**：受限 Toolkit（见下）+ 独立 hooks（`ToolPermissionHook` 从 **spec.permissionMode** 读，而非全局 config）+ 独立 `InMemoryMemory`。
- **受限 Toolkit 无现成"取子集"API**：现有 toolkit 是一次性 `registration().tool().apply()` 全量注册。按 `spec.toolNames` 得到子集须**新建一个 Toolkit 只注册白名单工具实例**。
- 建实例时解析 `spec.modelId` → `ModelStore` → `ProtocolRegistry` 建 `Model`（每 agent 各用各的模型）。

### 4. `AgentRunner`（运行层）
- **交互型**：由前端（REPL/Web）驱动，`stream(userMsg) → Flux<Event>`。
- **自主/定时型（= 数字员工，阶段 2）**：`schedule` 到点由 `TaskScheduler` 触发，起一个**隔离的一次性受限 agent**（同 `CompressionService.summarize` 范式，与 active 实例/会话完全隔离），在受限权限下跑 `mandate`，产晨报。折入原数字员工设计的全部要点：
  - 防重入（内存 `Set<runningId>`）；成功/失败/超时都产报告；跑完回写 `lastRunAt`。
  - 无人值守安全：无 confirmer → `ask` fail-closed；危险动作被 `PermissionDeniedTool` sentinel 拦 → `DeniedActionRecorder` 收集 → 进晨报「等你决定」；`commandAllowlist` 放行少数安全命令（如 `mvn test`）让守夜人能真干活。
  - **超时/中断（头等技术风险）**：`PigAgent.call()` 是同步 `.block()`，加硬超时不 trivial（`stream()` 数轮次 / 线程池 + `Mono.timeout`，且确认 LLM 请求能真被终止）→ **阶段 2 的 task 0 spike**。
  - 晨报：`workspace/reports/{date}/{id}.md`，含「我做了 / 我发现 / 等你决定」三段。

### 5. `AgentKernel`（门面）—— 前端适配层核心（本轮 point 3）
前端只依赖这一个内核 API：
```
listAgents() / getAgent(id) / createAgent(spec) / updateAgent(spec) / deleteAgent(id)
useAgent(id)                                  // 切换交互型当前 agent
chat(agentId, userMsg) -> Flux<Event>         // 交互流（CLI 流式 + Web SSE/WS 共用）
runNow(agentId) / enableSchedule/disableSchedule
subscribeEvents() -> Flux<KernelEvent>        // 会话/运行/报告事件，供 Web 可视化
```
- CLI 的 `AgentRepl` 改造成 `AgentKernel` 的一个 **CLI adapter**（行为不变）。
- 后续独立 spec 的 Web server 是另一个 adapter；channel 也走它。**加入口 = 加 adapter。**
- 事件流用 reactor `Flux`（契合现有 AgentScope reactive 栈）。

## 分阶段（每步独立可落地）

- **阶段 1 — 多 agent 管理内核 + 每 agent 模型**（point 1+2）
  `AgentSpec`(含 `modelId`) + `workspace/agents/` 持久化 → `AgentRegistry` 替换单 `AgentHolder`（现有单 agent = active 实例，行为不变）→ 每 agent 解析各自模型建实例 → `/agent list|use|new|model` 命令。
  **判据**：定义 2 个用不同模型的 agent，在 CLI 间切换，各用各的模型对话。

- **阶段 2 — 数字员工（自主/定时运行，多 agent 的第一个应用）**
  `AgentRunner` 自主分支 + `TaskScheduler` 接入 + 无人值守权限档 + `commandAllowlist` + 晨报 + **task 0 超时 spike** + 防重入 + `lastRunAt`。
  **判据**：定义一个带 `schedule` 的 agent，到点自主跑，产晨报，危险动作 defer 到「等你决定」。

- **阶段 3 — 前端适配层（门面 + CLI adapter）**（point 3 的地基）
  抽 `AgentKernel` 门面 + `KernelEvent` 事件流；`AgentRepl` 改造成它的 CLI adapter（行为不变）。**本设计到此为止**——它是承重墙工作的自然收尾。
  **判据**：CLI 完全通过 `AgentKernel` 驱动、行为不变；门面 API + 事件流就绪，可被别的入口消费。

- **（独立后续 spec）Web 可视化**（point 3 的应用）
  Web 是一个**独立大工程**，与承重墙耦合度低，**切成单独 spec**：嵌入式、无 DB、单用户的本地 server 暴露 kernel API + 事件流 + Web MVP（agent 列表/切换、会话流、运行监控、晨报收件箱、「等你决定」审批）。放在多 agent 内核 + 门面就绪之后做。

- **（可选深化）阶段 4 — agent 间委派/编排**
  sub-agent 即工具（一个 agent 能把另一个当工具调），仍进程内、无编排 DB。**明确标为可选**，视需要再做（守个人电脑简单性）。

## Open Questions

1. **多 agent 深度（需你确认边界）**：阶段 1–3 只做「管理 + 运行多个独立 agent」，**agent 间委派/编排列为可选阶段 4，先不做**（YAGNI）。这个边界对吗？
2. **单活会话 vs N 实例**：`SessionManager` 现假定唯一 `currentSessionId` + per-turn `saveCurrent`。多实例后交互仍单活（active 实例），但 registry 里**非 active 实例的会话谁存/何时存**要定清楚（建议：切走时存、非 active 不自动 per-turn 存）。
3. **并发 / 记忆隔离**：多 agent 同时运行需去掉热路径 `.block()`；`CompositeLongTermMemory.setSessionMemory` 是**单 `volatile` 字段**，并发下必踩，要改成每实例独立记忆。阶段 1 管理可先不并发，自主/Web 并发时再处理（task 0 spike 的延伸）。
4. **交互型 vs 自主型的统一**：都用 `AgentSpec`，靠 `schedule` 是否为空区分；二合一够不够，还是拆两类？倾向二合一。
5. **Web 技术栈**（留给独立 Web spec）：嵌入式（Javalin / Spring Boot 内嵌）+ 简单前端 vs 纯静态页 + SSE？倾向前者，单进程好带。

> 原「TaskScheduler 通用化 + cron 库」已从 Open Question **升级为阶段 2 的明确 task**（见 Next Steps）——`TaskScheduler` 不只硬绑 `Task` 类型，还硬绑 `taskManager.updateStatus`/`getTasksByStatus` 的 Task 生命周期，是真重构；且 `parseCronInterval` 只认 `*/N`，**「每晚定点」必须换真 cron 库（如 cron-utils）**。

## Success Criteria

- 阶段 1：能养多个 agent、各选模型、CLI 间切换。
- 阶段 2：一个 agent 能自主定时跑并产晨报，危险动作不擅自执行。
- 阶段 3：CLI 完全通过 `AgentKernel` 门面驱动、行为不变，API + 事件流就绪供别的入口消费。
- （独立 Web spec）：同一内核被 Web 入口驱动，可视化管 agent + 读晨报。
- 全程：单 agent 老路径行为不变；无 DB/服务端集群引入。

## Distribution Plan

CLI 随 `pig-agent-cli` 分发；（独立 Web spec 的）Web server **嵌入式随包**（单进程、无独立部署、无 DB）。跑在现有 24h 常驻进程里。CI（路线图 P1）覆盖构建。
