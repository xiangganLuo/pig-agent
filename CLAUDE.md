# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Pig Agent is a terminal-based AI agent framework for Java, built on **AgentScope Java** (`io.agentscope:agentscope` 1.0.12). It wraps AgentScope's `ReActAgent` and exposes it through a picocli + JLine3 REPL, with pluggable LLM providers, multi-model management, independent conversation sessions, a two-tier memory model, automatic context compression, built-in tools, MCP integration, task scheduling, and message channels.

The README (in Chinese) is a detailed reference for the original architecture; this file is the source of truth for the current build and module layout.

> Status note: the `pig-agent-session`, `pig-agent-model`, compression, and CLI-refactor code were added rapidly and have **not been verified to compile/run in this environment** (no local Maven). Run `mvn -pl pig-agent-cli -am compile` first and treat the first build as a verification pass.

## Build & Run

```bash
mvn compile                       # compile all modules
mvn test                          # run all tests (offline; jacoco instruments but does NOT gate here)
mvn verify                        # tests + jacoco per-module coverage-floor gate (ratchet); *IT stay skipped
mvn verify -Pit                   # also run the real-model *IT (needs a configured models.json)
mvn install                       # build + install to local repo
mvn exec:java -pl pig-agent-cli   # run the CLI REPL (main: io.pigagent.cli.PigAgentCli)
mvn -pl pig-agent-cli -am compile # compile the CLI and everything it depends on
```

> **CI quality gate (`ci-quality-gate`):** `mvn verify` enforces a **per-module jacoco line-coverage floor** (a ratchet set at "current − 2%", so coverage can't regress; stock jacoco has no cross-module aggregate `check`). `maven-failsafe-plugin` runs the `*IT` real-model tests only under `-Pit` (or `-DskipITs=false`); a credential-less `mvn verify` skips them and stays green.

Run a single module's tests, or a single test class/method:

```bash
mvn test -pl pig-agent-model
mvn test -pl pig-agent-config -Dtest=ConfigurationManagerTest
mvn test -pl pig-agent-task -Dtest=TaskTest#methodName
```

Requires **Java 17** and Maven 3.9+. Models are configured **interactively on first run** (the onboarding wizard writes `~/.pig-agent/workspace/models.json`) and stored there going forward — API keys are no longer read only from the environment, though env vars (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `DASHSCOPE_API_KEY`, `GEMINI_API_KEY`, `MIMO_API_KEY`; Ollama needs none) still work as a fallback. With no usable model, the wizard runs and cannot be skipped.

> The README's build commands show a trailing `-s ` settings flag — that is a stale leftover; no custom Maven settings file is used. Use the plain commands above.

### Protocol client SDKs
The provider module is organized by **protocol standard**, not vendor: 5 `ModelProtocol` implementations (`openai` / `anthropic` / `gemini` / `ollama` / `dashscope`). Any OpenAI-compatible vendor (Xiaomi mimo, DeepSeek, Kimi, Qwen-compat, …) is reached through the `openai` protocol + that vendor's base URL — no per-vendor class. AgentScope declares the SDKs as **optional**, so they are added explicitly in `pig-agent-providers/pom.xml` (versions matched to AgentScope 1.0.12 in the parent POM properties): `com.anthropic:anthropic-java` 2.14.0, `com.openai:openai-java` 4.28.0 (covers the `openai` protocol incl. all compatible vendors), `com.google.genai:google-genai` 1.45.0, `com.alibaba:dashscope-sdk-java` 2.22.9. A missing one surfaces as `NoClassDefFoundError`/unresolved import (e.g. `com.anthropic.client.AnthropicClient`) when that protocol builds its model.

## Architecture Essentials

**Wiring happens in `AgentBootstrap.build(...)`** (`pig-agent-cli`) — workspace, config, providers, model store/manager, the agent + kernel, sessions, compression, tasks, the channel agent, and MCP are all constructed and connected there, returned as an `AgentBootstrap.Services` holder. Read it first to trace how a component plugs in. **The CLI REPL is the primary frontend**, adding its own surface on top of `Services`: `PigAgentCli.main` (REPL + channel bridges + optional Web console). The embedded Web console has **returned** as the `pig-agent-web` module — a second `AgentKernel` adapter (HTTP + SSE over the kernel façade), started in-process when `web.enabled` (default off), sharing the one kernel with the REPL. "Add a frontend = add an adapter" now has two live examples (REPL + web).

**System prompt assembly (`system-prompt`).** The agent's system prompt is assembled in `AgentBootstrap.build` as `sysPrompt = workspace.readAgentMd() + "\n\n" + workspace.readInfoMd() + AgentBootstrap.TOOL_GUIDANCE`. `AGENT.md` is a **user-editable template** seeded once per workspace by `WorkspaceManager.defaultAgentMd()` via `createIfAbsent` (only new workspaces get the default; an existing user's `AGENT.md` is never overwritten). The seeded default is a **detailed, structured, English production-grade prompt** — sections for identity, operating principles, tool discipline (the real tools: `readFile`/`writeFile`/`listDirectory`, `executeCommand`, `fetchUrl`/`webSearch`, tasks/checklists, compute tools, MCP self-mgmt), skills (`listSkills`/`loadSkill` + the 7 built-in skills), safety/permissions & sandbox awareness, planning, output conventions (**reply in the user's language**), and error handling; it names only real tools/plugins/skills. `INFO.md` carries per-machine env. `TOOL_GUIDANCE` is a fixed release-owned constant (byte-stable per run) appended even when a user rewrites `AGENT.md`, so the always-on constraints survive: native-path file tools over the shell, graceful degradation when a tool is confirmed/denied/unavailable, and never echoing credentials. Change: `openspec/changes/system-prompt-optimization/`.

**The agent is swappable at runtime.** AgentScope's `Model` is fixed at build time, so to switch models without restarting, the `PigAgent` is built via `AgentFactory.create(model)` and stored in a mutable `AgentHolder`. Everything (REPL, channels, session manager, compression) reads the current agent through the holder. `ModelManager.ensureModel(...)` rebuilds the agent on a model switch; the session layer reloads the conversation afterward.

**Multiple agents (`agent-management`, phase 1).** The single `AgentHolder` is driven by an `AgentRegistry` (`Map<agentId, AgentInstance>`): the holder is a **live view of the active instance**, so every existing reader stays unchanged. Each agent is a declarative, immutable `AgentSpec` — its own model (`modelId` → `ModelManager.modelFor`, fault-tolerant fallback to default), tool subset (`AgentWiring.toolkitFor` = `Toolkit.copy()` + `removeTool` by whitelist), and permission mode (per-agent `ToolPermissionHook` mode-override) — persisted at `workspace/agents/{id}.md` (`AgentSpecRepository`, YAML front-matter + prompt body) and built by `AgentInstanceFactory` (per-agent toolkit/hooks/memory; NOT the shared `AgentFactory`). On an empty `agents/`, a `default` instance equivalent to the old single agent is bootstrapped, so single-agent behavior is unchanged. Operate via `/agent list|use|new|model`. Design: `docs/design/agent-management-design.md`; change: `openspec/changes/multi-agent-kernel/`.

**Kernel façade (`AgentKernel` + `KernelEvent`, `agent-kernel-facade`).** The frontend drives the kernel through the single `io.pigagent.core.agent.kernel.AgentKernel` façade — `listAgents/getAgent/activeId/useAgent/createAgent/updateAgent/deleteAgent/chat/runNow/interruptCurrent/subscribeEvents` — and depends **only** on it, never on the internal `AgentRegistry`/`AgentInstanceFactory`/`AgentSpecRepository`/`AgentRunner` (the façade orchestrates those). "Add a frontend = add an adapter": `PigAgentCli.main` builds one `AgentKernel` and injects it into `AgentRepl`; `ReplContext` exposes only the kernel and `AgentCommand` (`/agent …`) calls through it. A REPL chat turn streams via `kernel.chat(activeId, msg)` (which registers an interruptible turn), so mid-turn Ctrl-C → `kernel.interruptCurrent()` cancels the in-flight model call. Lifecycle events (`KernelEvent`: `AGENT_CREATED/DELETED/SWITCHED`, `CHAT_STARTED`, `RUN_STARTED/FINISHED`, `REPORT`) are published on a `Sinks.many().multicast()` hot `Flux` via `subscribeEvents()` — no subscribers = zero cost. **Channels are a façade-visible separate track (D4):** each channel keeps its own `channelHolder` + channel-mode permission agent and is **not** a switchable kernel agent (that would leak the no-confirmer channel agent into `/agent use`); `ChannelAgentBridge` takes an optional `AgentKernel` and calls `noteChannelChat(channelId)` so channel turns surface as `CHAT_STARTED` events tagged `channel:<id>` — visible, not owned.

**CC-style REPL rendering (`tui-frontend`, capability `cc-repl`).** The REPL is a Claude-Code-style **line-based** conversational front-end (never full-screen). A chat turn streams via `kernel.chat` and is rendered incrementally by `repl/render/`: `MarkdownAnsiRenderer` (pure `**bold**`/`` `code` ``/```` ``` ````-fence/`- list`/`# heading` → ANSI), `StreamingMarkdownPrinter` (flushes each complete answer line as its newline arrives, tracking fenced-code state across chunks), and `ToolCallFormatter` (tool calls render as `⏺ toolName` / `  └ result summary`, single-line + truncated, with `redact(...)` masking `sk-`/`key=`/`Bearer` secrets — credentials MUST NOT appear in REPL output). Reasoning shows a `⋯ thinking` spinner cleared when the answer/tool output begins. A one-line `StatusLine` (`model · session · perms`, model via `StoredModel.label()`, no credentials) prints above each prompt. `repl/select/` provides an arrow-key inline picker (`InlineSelector` + pure `SelectorModel`); `/model` with no args pops it (Enter selects, Esc/q cancels), degrading to numeric input on a non-interactive terminal, then `ModelSelection.apply` tests + activates the model.

**REPL flow:** `AgentRepl` builds a JLine `Terminal` (jna provider, `jansi(false)`) and a picocli command tree (`ReplCommands`) via `picocli-shell-jline3`. A line starting with `/` is dispatched to a picocli subcommand (`/model`, `/agent`, `/session`, `/memory`, `/compress`, `/tasks`, `/help`, …) — typing `/` **auto-pops** a completion menu covering **all** commands (picocli metadata via `SystemRegistry.completer()`) with no Tab: `SlashCompletionWidgets` overrides the printable-range `self-insert`/`backward-delete` to re-run `expand-or-complete` after each keystroke **only while the buffer is a slash command** (pure gate `SlashCommands.isCommandBuffer` + non-empty `matching(...)`), so the list narrows live (`/mo` → `/model`) and normal chat input is untouched; `↑/↓` are rebound to `menu-complete`/`reverse-menu-complete` while a slash buffer is active (else history). It is installed only on a real TTY (dumb terminals degrade to plain Tab completion). Anything else is a chat turn: `runTurn` does `noteUserMessage → maybeCompress → kernel.chat(activeId, msg) → renderStream → saveCurrent`. `renderStream` subscribes with a `CountDownLatch` and installs a SIGINT handler so **mid-turn Ctrl-C** calls `kernel.interruptCurrent()` + disposes the subscription and returns to the prompt (the process does NOT exit); the previous INT handler is restored in `finally`. At the prompt, idle Ctrl-C discards the line (`UserInterruptException`), Ctrl-D exits (`EndOfFileException`) — three states that don't cross-contaminate. Output is colored with **Jansi as a string builder only** — `AnsiConsole.systemInstall()` is intentionally NOT called (it double-wraps `System.out` and garbles output on Windows when JLine owns the terminal). See `cli/Ansi.java`. **Terminal requirement:** JLine needs a real console — use Windows Terminal / PowerShell / cmd; under git-bash/mintty stdin is not a real TTY, so run via `winpty` or use Windows Terminal.

**Sessions** (`SessionManager`): each conversation is isolated. Conversation history persists via AgentScope's `JsonSession` under `workspace/sessions/{id}/`; lightweight metadata (`Session` record) is stored as `meta.json` by `FileSystemSessionRepository`. Switching = save current → `clearMemory` → `loadIfExists(target)` (no agent rebuild unless the model differs). `current-session-id` in config restores the last session on startup.

**Two-tier memory** (`CompositeLongTermMemory`, a `LongTermMemory`): a shared **global** store (`workspace/context/memory.md`) plus a swappable **per-session** temp store (`sessions/{id}/temp-memory.md`). `retrieve` merges both with source labels; `record` writes only to the session tier; a global enable flag (`/memory on|off`) gates all of it. Memory is injected via a pig-owned `EphemeralMemoryContextHook` (`pig-agent-core`), **not** AgentScope's `STATIC_CONTROL` wiring: `PigAgent` deliberately does NOT call `.longTermMemory(...)` on the `ReActAgent`, because that mode's `StaticLongTermMemoryHook` injects on `PreCallEvent` — a list that flows through `doCall → addToMemory` and thus gets **persisted into the conversation history and accumulates a memory snapshot every turn** (a bug). Instead the hook injects the retrieved memory as a trailing user-side message on **`PreReasoningEvent`** (whose list is rebuilt from `[system] + memory.getMessages()` each reasoning step and never written back to memory) — so injection is truly **ephemeral**: it reaches the model, keeps the system prompt byte-stable across turns (prefix-cache friendly), and never pollutes/grows the persisted history. `record` is preserved on `PostCallEvent` (delegates to `CompositeLongTermMemory.record`, session-tier only; no-op when disabled). Change: `openspec/changes/prefix-cache-context/`.

**Context compression** (`CompressionService`): operates only on the in-memory conversation (never on persisted history or memory). When an estimated token budget (config `compression`) is exceeded it summarizes older turns via a throwaway agent on the current model and keeps the most recent turns; `/compress now|status|off|on`. **Compression derives a session lineage (record-only, no UI)** (`compression-lineage`): after a successful compression, an optional `CompressionLineageRecorder` (core seam; implemented by `SessionLineageWriter` in the session module, wired in `AgentBootstrap`) writes provenance into the session metadata — `Session.lineageId` (stable across the compression chain, assigned on first compression) + `parentSessionId` (the just-superseded pre-compression state), via `Session.withCompressionLineage()`. It is lightweight (same session id, no new session dir, no snapshot content) and **independent of the compression core**: it runs only after memory is rewritten and any failure is logged and swallowed, so it never breaks compression. Old `meta.json` without lineage fields reads back as no-parent (fault-tolerant). Queryable via `SessionManager.lineageOf(id)` for a future TUI; nothing is displayed yet.

**Dynamic MCP management** (`McpManager` + `JsonMcpStore`): MCP servers are CRUD-managed at runtime and persist to `workspace/mcp.json` (the source of truth, keyed by name). On first run, legacy `application.yaml`'s `mcp.servers` are imported once into `mcp.json`. `McpManager` holds the `Toolkit` plus a `name→McpClientWrapper` map and registers/unregisters MCP tools live. Concurrency uses a **fine-grained lock (E1)**: network/process connect + `listTools` run *outside* the lock; only the short collision-check + `registerMcpClient` + `map.put` critical section is `synchronized(this)`. Tool namespace is **flat (D-NS)**: adding a server whose tool name collides with an already-registered tool is refused. Operate via `/mcp list|add|remove|edit|enable|disable|test` (operator-facing, full trust — may add stdio servers). The agent can self-manage MCP via the `McpTool` (`@Tool`), gated by the **D-SEC** security door (`mcp.agent-management`): `allow-add`/`allow-remove` default **off**; when add is enabled, only URL servers whose host is in `allowed-hosts`, after human confirmation, are accepted (never stdio/command); `list`/`test` are always allowed; `env`/`headers` are redacted in tool output to avoid credential echo.

**Tool availability gating** (`io.pigagent.tool.availability`): the **first-line filter** deciding whether a tool is even visible to the model, applied when the toolkit is assembled in `AgentBootstrap` (`ToolAvailabilityGate.applyTo(toolkit, builtins)`) — orthogonal to and stacked *before* the permission veto (availability = visibility; permissions = may-a-visible-tool-run). A built-in tool MAY implement the optional, **non-invasive** `ToolAvailability` interface (`availabilityToolNames()` + `checkAvailability() → Availability`) to declare a runtime precondition; tools that don't implement it are always available (backward compatible). Unavailable tools are `removeTool`-ed from the shared toolkit so they never enter the model schema (prevents hallucinated calls, saves tokens); a check that throws is **fail-safe → unavailable** and never blocks other tools. The gate returns an immutable `ToolAvailabilityReport` (list of `(toolName, reason)`) carried on `Services`/`ReplContext` and shown by `/status` — reasons name the missing prerequisite only (e.g. `BRAVE_API_KEY not set`), **never a credential value**. Example: `BraveWebSearchTool` gates `webSearch` on `BRAVE_API_KEY`. Availability is evaluated once at bootstrap (no runtime re-eval / hot schema swap; MCP tools' availability is their connection state, per the existing `McpManager`).

**Deferred tools + `tool_search` (`deferred-tools`, `io.pigagent.tool.deferred`, off by default).** A *dynamic, on-demand* visibility layer stacked on top of the (static) availability gate — borrowed from deerflow's `DeferredToolFilterMiddleware`: large/rarely-used tools (especially as MCP servers grow) are kept OUT of the model's **initial** tool schema to save every-turn prompt tokens, and the model discovers + enables them on demand via a built-in **`tool_search`** (`READ_ONLY`, in `ToolRiskClassifier`). **Mechanism = AgentScope's native tool groups** (verified by decompiling 1.0.12): a tool parked in an **inactive** group is excluded from `Toolkit.getToolSchemas()` (`ToolSchemaProvider`) *and* rejected at call time (`ToolExecutor.executeCore` → "Unauthorized tool call"), so **defer = inactive group; reveal = activate the group** (`updateToolGroups(...,true)`, a pure flag flip — the tool object is never removed/re-registered, so execution wiring, the `GuardedAgentTool` wrapper and MCP `mcpClientName` are all untouched). This is strictly cleaner than remove/re-add, whose re-registration would drop `mcpClientName` and break `McpManager.removeMcpClient`. `DeferredToolPlanner` (pure Strategy) decides what to defer from config `tools.deferred` (`enabled`, explicit `tools` list, and an `auto-defer-mcp` + `threshold` rule that defers all MCP tools once the total tool count exceeds the threshold, default 25); `DeferredToolGate` applies it — built-in/plugin tools go into a per-tool inactive group (`deferred__<tool>`, re-registering their current `AgentTool`), MCP tools are deferred by deactivating the `mcp:<server>` group they were registered into **at attach time** (`McpManager.setToolGroupNamer` → `registration().mcpClient(...).group(g)`, MCP-safe). `DeferredToolRegistry` holds each deferred tool's name+description+keywords+group; `tool_search` ranks a query against them, reveals the matches (activates their group; MCP reveal is per-server), and returns their names+descriptions (empty/no-match → a helpful hint listing searchable names). Wired in `AgentBootstrap`: when enabled, `tool_search` is registered **before** `ToolContractGuard.install` (so it's guarded and never re-registers MCP tools) with the same registry the gate later populates after MCP attaches. **Default off = zero behavior change** (no tools hidden, no `tool_search`, no MCP grouping). **Limitations:** evaluated once at bootstrap (hot-added MCP servers stay visible until restart, like the availability gate); MCP reveal granularity is per-server; `Toolkit.copy()` per-agent instances don't share reveal state.

**Tool permissions** (`io.pigagent.tool.permission`, gated by `permissions` config): a high-priority `ToolPermissionHook` (`PreActingEvent`, `priority()=0`) vetoes tool calls per a global **mode** — `plan` (read-only: deny all mutating tools so the agent only produces a plan), `ask` (default; confirm each mutating tool y/a/N), `auto` (auto-allow edits/network, still confirm exec/mcp-admin), `bypass` (allow all). Tools are risk-classified (`ToolRiskClassifier`: READ_ONLY/WRITE/EXEC/NETWORK/MCP_ADMIN; unknown → EXEC fail-safe; `tool-overrides` can reclassify). The **veto mechanism** (proven by `PermissionVetoSpikeIT`): the hook rewrites the pending `ToolUseBlock` to a read-only `PermissionDeniedTool` sentinel — the real tool never runs and the model gets the denial as a tool result and continues. `a`(always) persists to `permissions.allowlist` (tools + normalized command keys for EXEC, first-token). MCP_ADMIN is delegated to the existing **D-SEC** door (no double-prompt). Operate via `/permission status|mode|channel-mode|allow|revoke|reset|list`. Default `ask` changes prior behavior (was effectively bypass) — `/permission mode bypass` restores it. Channels run through a **separate channel agent** whose hook uses `channel-mode` (default `auto`) with no confirmer (ASK fails closed); `ModelManager.attachChannel` rebuilds it on model switch so channels still follow the active model. Pure logic (`PermissionPolicy`/`PermissionResolver`) is unit-tested; the hook is a thin adapter.

**Tool return contract (`tool-json-contract`, `io.pigagent.tool.contract`):** built-in `@Tool` tools follow a uniform result contract — success returns the tool's normal output, **failure returns a canonical `{"error":"<reason>"}`** (build it with `ToolErrors.message(...)`), never an exception, and the reason is credential-redacted (`CredentialSanitizer`, aligned with the model/mcp "never echo a key/token" convention). A **dispatch-layer safety net** backs this up: `ToolContractGuard.install(toolkit)` (called in `AgentBootstrap`) wraps every built-in tool in a `GuardedAgentTool` decorator so *any* exception a tool lets escape — sync throw, failing `Mono`, or null — becomes a canonical error result (logged at `warn` with the stack, sanitized) instead of aborting the turn. Two layers (tool self-guard + dispatch guard) mean either alone stops an exception from propagating. The guard is installed **before MCP servers attach** so it never re-registers live MCP-server tools (which AgentScope manages by `mcpClientName`); `Toolkit.copy()` per-agent toolkits inherit the guarded built-in tools.

**Tool egress sandbox & credential hardening (`tool-sandbox-and-secrets`, capabilities `tool-sandbox` + `credential-hardening`):** a third orthogonal tool guard, stacked *after* availability (visibility) and permissions (may-run) — it bounds what a *visible, permitted* tool can reach, and hardens credential handling. **File egress:** `FileSystemTools` `readFile`/`writeFile` refuse the workspace credential files (`models.json`/`mcp.json` + `.bak`) — this is a **credential-file blacklist, NOT a workspace sandbox** (this is a coding agent; arbitrary project files stay accessible). Matching normalizes to the resolved real path (`toRealPath`, else `toAbsolutePath().normalize()`), remembering both forms, so `../` traversal and symlinks are caught. **Web egress (SSRF):** `SmartWebFetchTool.fetchUrl` runs `SsrfGuard.checkBlocked` first — it resolves the host via `InetAddress.getAllByName` and blocks if **any** resolved IP is loopback/any-local/link-local(`169.254`)/site-local-private/IPv6-ULA/multicast (judging the **resolved IP**, not the literal host, defeats decimal-IP/`[::1]`/DNS-points-inward), rejects non-`http(s)` schemes, keeps `Redirect.NEVER`, and honors an optional `tools.web.allowed-hosts` allowlist. Blocked tools return the canonical `{"error"}` (no exception, no internal IP echoed). Both guards get their deps (`workspaceRoot`, `webAllowedHosts`) via `ToolContext` from `AgentBootstrap`; **safety defaults need no config** (blacklist auto-on from the workspace root, SSRF always blocks private ranges). **Credential hygiene:** API-key / sensitive-value entry is masked (REPL `/model add|edit` and `/mcp add|edit` sensitive keys via JLine `readLine(prompt,'*')`; `OnboardingWizard` via `Console.readPassword`, degrading to a visible read + one-time warning with no console); `JsonModelStore`/`JsonMcpStore` restrict the written file to `0600` on POSIX (`restrictToOwner`, ignored on non-POSIX). Credentials still stored plaintext (rely on `0600` + directory perms — do not use on a shared host). Resolves the review's P0 #1–4 and MCP security follow-ups M-1/M-2.

**Command-execution sandbox (`exec-sandbox`, P1 of the sandbox system).** A fourth orthogonal guard specific to `ShellTools.executeCommand` — the "constrained-run" layer, stacked *after* the permission veto (may-run): permissions decide *whether* a command runs, this decides *how constrained* it is while it runs (a permitted `rm -rf /` is still blocked here; a normal command only gets the runtime bounds). Two collaborators live in `io.pigagent.tool.sandbox`: a config-backed immutable value object `SandboxPolicy` and a Strategy `CommandGuard` that is the single home of the denylist / output-cap / env-scrub logic (not scattered in `executeCommand`). Four constraints: **(1) output cap** — `capOutput(InputStream)` does a *bounded* read (default 200 KB), draining/discarding the remainder to avoid pipe-deadlock and appending a truncation marker (replaces the OOM-prone `readAllBytes()`); **(2) configurable timeout** (default 30s, was hardcoded); **(3) a conservative catastrophic-command denylist** — a compiled-in floor (root/home deletes, `mkfs`/`format`/`diskpart`, pipe-to-shell installs, fork bombs, `shutdown`/`reboot`, `dd of=/dev/…`, `chmod -R 777 /`) that config `exec.denylist` can only *extend* (never weaken); classification is **two-pass, three-tier, most-severe-wins** (`block` > `warn` > `pass`) to resist operator bypass — structural patterns scan the whole normalized command, then it splits on shell operators (`; && || | &`, *quote-aware*) and matches single-command rules per sub-command, so `echo ok && rm -rf /` is caught while `git commit -m "a && b"` is not; cheap input validation (empty / >10 000 chars / NUL byte) runs first; **(4) env credential scrubbing** (default on) — strips credential-bearing vars (`*_KEY`/`*TOKEN*`/`*SECRET*`/`*PASSWORD*`/…) from the child so a command can't `echo $ANTHROPIC_API_KEY`, keeping PATH/HOME/etc; plus an optional `exec.working-dir`. Config lives under `sandbox.exec` in `application.yaml` (all optional, default-safe; a malformed cap/timeout clamps to the default). Wired like the other tool guards: `AgentBootstrap` builds a `SandboxPolicy` from config and injects it via `ToolContext` → `ShellToolsProvider` → `ShellTools`; no config = conservative defaults. Blocked commands return the canonical `{"error":"blocked: <category>"}` (reason names the category only, never the command; the audit-log line redacts the command via `CredentialSanitizer` + truncates). **Honest limitations:** this is a best-effort in-process boundary, **not OS-level isolation** (no seccomp/namespaces/containers — that's P3) and the denylist is a "resist foot-guns / prompt-injected disasters" filter, **not** a barrier against a determined adversary (base64/alias/variable tricks defeat any regex denylist); autonomous/channel-specific tightening is P4. **Middle "warn" tier (D12, `sandbox-warn-tier`):** the classifier is now three-tier — a conservative built-in **warn set** (`pip install`, `apt`/`apt-get install`, `sudo`/`su`, non-root `chmod 777`, `PATH=` reassignment, `npm install -g`; extendable via `sandbox.exec.warnlist`, carried on `SandboxPolicy.extraWarnPatterns`) flags medium-risk-but-legitimate commands. A warn-matching command (that isn't also a block) **runs normally** but `ShellTools` appends a `⚠️ Warning: <category>` note to the tool result so the model sees the risk; `CommandGuard.classify` reuses the same two-pass structure (`checkDenied` is now a block-only view of it, so the block/pass contract and every prior test are unchanged). Warn is **purely additive** — most-severe-wins keeps block strictly ahead of warn, and normal dev commands (mvn/git/npm run/ls) stay silent. Same best-effort caveat as the denylist (regex, not an adversarial boundary).

**Tool-call loop detection (`loop-detection`, `io.pigagent.core.loop`).** A fifth orthogonal safety net catching the "same action, over and over" failure mode (re-`readFile` the same file, re-run the same failed command, retry after a wall) that burns tokens and never converges — a mode the veto/availability/contract/sandbox guards don't cover. Borrowed from deerflow's `LoopDetectionMiddleware`. **Strategy + Adapter design:** a pure, offline-tested `LoopDetector` keeps a sliding window (default 20) of recent tool-call *signatures* and maps the current signature's repeat count to a `LoopDecision` — `WARN` at ≥ `warn-threshold` (3), `STOP` at ≥ `stop-threshold` (5); the window evicts the oldest when full and bad config is clamped (`window/warn ≥ 1`, `stop ≥ warn`). How a call folds to a signature is a swappable `ToolCallSignatureStrategy`; the default **buckets `readFile` by 200-line ranges** (`readFile|<path>|#<startLine/200>` — so re-reading nearly the same region counts as a repeat; a paramless read of one path collapses to bucket 0) and **hashes full args for `writeFile`/edits/everything else** (`toolName|sha256(canonical(input))`, key-order-independent — so writing different content is never a repeat). The thin adapter `LoopDetectionHook` (a `Hook`, `priority()=10` — **after** the permission veto's `0` so it never interferes; before the logging hooks) plugs the detector into events: on `PreActingEvent` it observes the pending `ToolUseBlock` (skipping the sentinels in its ignore set — its own `loopDetected` + `permissionDenied` — and bypassing entirely when disabled), and on `STOP` **reuses the veto-to-sentinel mechanism** — rewriting the block to the read-only `LoopDetectedTool` (`loopDetected`, in `pig-agent-tools`, name sourced from `LoopDetectionHook.SENTINEL_TOOL_NAME`) so the real tool never runs and the model is told to stop and answer; on `WARN` it queues a nudge that it injects on the next `PreReasoningEvent` as a trailing user-side `Msg` — **reusing the ephemeral injection path** of `EphemeralMemoryContextHook` (rebuilt each step from `[system]+memory`, never persisted). The hook **resets the detector per turn** by watching the USER-message count in the reasoning input (change ⇒ new turn / session switch ⇒ `reset()`), so counts never leak across turns. Config `loop-detection` (`enabled` default true, `window-size` 20, `warn-threshold` 3, `stop-threshold` 5) is all-optional/default-safe/back-compatible; `enabled: false` fully bypasses. `AgentBootstrap` gives the interactive and channel agents each their own detector instance (autonomous one-shot agents get a fresh window per run, so they self-reset). Change: `openspec/changes/archive/2026-07-15-loop-detection/`.

**Extension is via SPIs, not core edits:**
- New tool: a class with `@Tool`/`@ToolParam` methods is **auto-discovered via SPI** (`tool-autoregister`) — add a tiny `io.pigagent.tool.spi.ToolProvider` impl (in `pig-agent-tools`) that returns `new MyTool(...)` (pulling deps from `ToolContext`) and list it in `META-INF/services/io.pigagent.tool.spi.ToolProvider`; `ToolRegistrar.registerAll` in `AgentBootstrap` picks it up with no wiring edit. Manual registration (`toolkit.registration().tool(new MyTool()).apply()`) still works as a fallback/override: a manually-registered tool overrides a same-named auto one (INFO audit), unexpected same-name duplicates keep the first (WARN, never stacked), and a single tool that fails to load/instantiate is isolated and skipped (fail-safe). Set `-Dpigagent.tools.auto-register=false` to fall back to pure-manual wiring. Auto-registration only decides whether a tool enters the Toolkit — permission veto / availability / return contracts are unchanged. For the tool's own body: return its normal output on success and `ToolErrors.message(reason)` on failure (canonical `{"error"}`, credential-redacted); don't throw as the model-facing error path (the dispatch guard is a net, not the primary contract).
- New hook: implement `io.agentscope.core.hook.Hook` (1.x event model: `PreReasoningEvent`/`PostReasoningEvent`/`PreActingEvent`/`PostActingEvent`; lower `priority()` runs earlier; return `Mono.just(event)`).
- New model protocol: implement `ModelProtocol` (`io.pigagent.core.protocol`) — note `protocolId()` + `createModel(ModelSpec spec)` (apiKey + optional baseUrl + modelName), plus `supportsBaseUrl()`/`requiresApiKey()` — and register on `ProtocolRegistry` in `PigAgentCli`. Adding a new *vendor* on an existing protocol (e.g. another OpenAI-compatible endpoint) needs **no code** — the user just picks the protocol and enters its base URL.
- New channel: implement `Channel`, register on `ChannelRegistry`; `ChannelAgentBridge` (holds an `AgentHolder`) routes channel messages through the agent.
- New plugin (`plugin-system`, module `pig-agent-plugin`): a **plugin** bundles several extensions behind one entrypoint — implement `io.pigagent.plugin.Plugin` with `register(PluginContext ctx)` and contribute via `ctx.addTool(...)` / `ctx.addHook(...)` (pulling deps from `ctx.toolContext()`). Discovery has two sources: classpath `ServiceLoader<Plugin>` (declare in `META-INF/services/io.pigagent.plugin.Plugin`) and external jars dropped in `workspace/plugins/` (`URLClassLoader`+`ServiceLoader`). `AgentBootstrap` runs `PluginRegistry.loadAndRegister(...)` **after** built-in tool auto-registration, so plugin tools **compose** with `ToolRegistrar` (same first-wins de-dup — a built-in wins a name collision, the plugin tool is skipped, never stacked) and plugin hooks are appended to the interactive agent's hook chain. A plugin whose `register` throws is isolated and its partial contributions discarded (fail-safe); a failing discovery source is skipped. No plugins → behavior is identical to today. External jars are arbitrary un-sandboxed code — only drop trusted jars. (Command/channel contributions are a deferred extension point; the current surface is tools + hooks.) The **`pig-agent-plugin-builtin`** module (`plugin-collection`) is the shipped reference example: six common, safe, offline **compute** plugins (time/timezone/epoch, UUID, Base64, md5/sha-256 hash, JSON pretty/validate, random) — pure-compute `READ_ONLY`, `{"error"}` contract — **plus** the non-core tools extracted from `pig-agent-tools` by `tools-core-slim`: `WebSearchPlugin` (`webSearch`, still availability-gated on `BRAVE_API_KEY`), `WebFetchPlugin` (`fetchUrl`, `SsrfGuard` + `tools.web.allowed-hosts` injected via `PluginContext.toolContext()`), `ChecklistPlugin` (`checklist`). All organized by the same GoF patterns — `AbstractToolPlugin` (Template Method for the `register` skeleton + Factory Method `createTools(ctx)`), each concrete plugin a `ServiceLoader`-discovered strategy, and `PluginCatalog` as the registry/single-source-of-truth (a test guards it against the `META-INF/services` file). Risk levels stay correct via the central `ToolRiskClassifier` name→risk catalog (`webSearch`=READ_ONLY, `fetchUrl`=NETWORK), which is module-agnostic (string keys). (`tools-core-slim` also removed the dead Lucene-based `ToolDiscovery` from `pig-agent-tools`.)
- MCP servers are managed dynamically (see below); their tools auto-register into the Toolkit and can be hot-added/removed without restart.

**Built-in skills (`builtin-skills`).** A *skill* is a named `SKILL.md` capability pack the agent pulls on demand via `SkillsTool` (`listSkills`/`loadSkill`). `SkillsTool` is no longer a single-directory scanner: it composes several `SkillSource`s (a Strategy abstraction in `pig-agent-tools`, `io.pigagent.tool.skills`, mirroring `PluginSource`) through a `SkillRegistry`. Two sources ship: **`ClasspathSkillSource`** (the built-in set — discovers `SkillProvider` SPI impls on the classpath via `ServiceLoader`, mirroring `ServiceLoaderPluginSource`) and **`WorkspaceSkillSource`** (`workspace/skills/<name>/SKILL.md`, mirroring `DirectoryPluginSource`). The curated built-in skills live in the **`pig-agent-skills-builtin`** module as classpath resources, enumerated by `SkillCatalog` (single source of truth, a drift test guards it against the resources) and exposed by one `BuiltinSkillProvider` declared in `META-INF/services/io.pigagent.tool.skills.spi.SkillProvider`. Seven ship today: `code-review`, `systematic-debugging`, `tdd`, `refactoring`, `git-commit`, `security-review`, `planning`. The registry de-dups by name with the **workspace source winning** (listed first), so a user can override/shadow a built-in skill by dropping a same-named `SKILL.md` into the workspace; `listSkills` shows the union (deduped), `loadSkill` resolves workspace-over-built-in. `SkillsTool`'s `@Tool` names/signatures are unchanged (no model-facing regression), and its `SkillsTool(Path)` convenience constructor composes both sources — so with the module absent the classpath source finds nothing and behaviour is exactly workspace-only (backward compatible). Wired for free through the existing `SkillsToolProvider` (`pig-agent-cli` depends on `pig-agent-skills-builtin` so the resources are on the runtime classpath); no `AgentBootstrap`/`ToolContext` change.

**Configuration** is split: model configs (+ `defaultModelId`) live in `workspace/models.json` (`JsonModelStore`); everything else (`agent`, `channels`, `mcp.agent-management`, `compression`, `current-session-id`, `memory-enabled`) lives in `workspace/application.yaml`, parsed by Jackson YAML into `PigAgentConfig`. `ConfigurationManager.updateConfig(Consumer)` persists and notifies listeners. The legacy `model:` block in YAML is kept for display/back-compat but `models.json` is the source of truth; likewise the legacy `mcp.servers` block is imported once then `mcp.json` is the source of truth.

**Model retry** (`io.pigagent.core.retry`): model streaming calls auto-retry **transient** upstream failures (HTTP 5xx like 502/503, timeouts, network/IO) — **permanent** errors (4xx/auth) fail fast. Config lives under `model.retry` in `application.yaml` (`enabled` default true, `max-retries` 10, `first-backoff-ms` 500, `max-backoff-ms` 8000 → exponential backoff with cap). Retry is driven by **error signals**, not a client-side clock: `per-attempt-timeout-seconds` still defaults to **0 (disabled)** (slow-but-healthy large-model responses legitimately exceed short timeouts), but with the `interruptible-run` capability it is now **safe to enable** (`> 0`): a stalled attempt is interrupted (its underlying `model.stream` subscription is cancelled, no half-output lands in history) and retried per the backoff policy, guarded by the same **pre-emission guard** so an attempt that has already streamed content is never re-run on a later timeout. `TransientErrorClassifier` classifies by status-token + exception type; `RetryPolicy` is applied by a `RetryingModel` **`Model` decorator** — retry wraps the underlying `model.stream` (a fresh HTTP call via `Flux.defer`) <em>inside a single agent invocation</em>, NOT `reactAgent.stream`. This is deliberate: `ReActAgent` is single-flight, so re-subscribing its stream re-enters a still-running agent ("Agent is still running"). `AgentFactory.create` wraps the model when a policy is present, covering interactive + channel by construction; the `ModelManager.test` probe skips `AgentFactory` → no retry. A **pre-emission guard** means once any content has streamed, a later failure is NOT retried (re-subscribing would regenerate from scratch and duplicate output). The `ModelManager.test` connectivity probe has no policy → stays fast-fail. `enabled: false` fully bypasses (legacy behavior). Retries are surfaced to the user (`[retry k/N] …`).

**Digital employee (autonomous agents)** (`io.pigagent.core.agent.runner`): an `AgentSpec` with a non-blank `schedule` (a cron expression) is autonomous — `PigAgentCli` registers it with the generalized `TaskScheduler.schedule(id, TaskSchedule, Runnable)` (real 5-field cron via cron-utils, e.g. `0 2 * * *`), which fires `AgentRunner.run(spec)`. `AgentRunner` builds an **isolated one-shot agent** (never the active instance; independent memory), runs the spec's `mandate` unattended, and writes a three-section morning report (`我做了 / 我发现 / 等你决定`) to `workspace/reports/{date}/{id}.md` (`FileReportWriter`). Safety: no confirmer → `ask` fail-closed; the agent's `commandAllowlist` (merged into the permission allowlist) lets it run a few safe commands (e.g. `mvn test`); everything else dangerous is vetoed and its `DeniedActionRecorder` surfaces it under「等你决定」. Timeout is **best-effort** (background thread + `Future.get`/`cancel`; `ReActAgent` is not truly interruptible — same constraint as model-retry, so it marks TIMEOUT and reports but never re-subscribes). Reentrancy-guarded; every run (success/failure/timeout) writes a report and updates `lastRunAt`. Operate via `/agent run <id>` (run now) and `/agent report`. Sample: `docs/examples/nightwatch.md`.

**Tasks** persist as Markdown at `workspace/tasks/{date}/{id}.md` (recurring under `tasks/recurring/`); `TaskScheduler` runs ONCE/CRON/DELAYED schedules on a `ScheduledExecutorService`.

**Autonomous guardrails** (`autonomous-guardrails`): three production safety nets. (1) `maxIters` now bounds **every** agent via `PigAgent.Builder.maxIters` (only applied when `> 0`, preserved across model switches) — interactive/channel take `agent.max-iters` (default **40**), per-agent/autonomous take `AgentSpec.maxIters` (default **10**, conservative for unattended runs). (2) Task `.md` persistence is **lossless** — the Schedule line encodes `ONCE` / `CRON:<expr>` / `DELAYED:<seconds>` plus `Created`/`Updated` timestamps + description, so CRON/DELAYED tasks survive a restart and are re-scheduled by `scheduleAll` — and **fault-tolerant**: a corrupt/incomplete task file is skipped with a warn (never crashes `findAll`/startup `scheduleAll`), and old type-only Schedule lines degrade to `ONCE`. (3) `PigAgentConfig` ignores unknown fields (`@JsonIgnoreProperties(ignoreUnknown = true)`) so config schema drift no longer fails the whole load and reverts every setting to defaults.

## Conventions

- **Immutability is enforced.** Domain types (`Task`, `Session`, `StoredModel`, `ProviderCredentials`, config events) are records; mutate via `withXxx()` copy methods. See `.claude/rules/common/coding-style.md`.
- File-backed repositories are **fault-tolerant**: a single corrupt file (bad `meta.json` / `models.json`) is skipped or backed up, never crashes the listing. Follow that pattern for new persistence.
- Tests use **JUnit 5 + Mockito + AssertJ**, AAA structure (test classes in `config`, `core`, `task`, `workspace`, `session`, `model`, and `cli`).
- Async/reactive APIs from AgentScope use Project Reactor (`Mono`/`Flux`); streaming consumes a `Flux<Event>` and filters on `EventType`.
- **Logging is SLF4J + Logback** (`logging-framework`). Every class logs via `private static final Logger log = LoggerFactory.getLogger(X.class)` with parameterized messages (`log.info("... {}", x)`); do NOT use `System.out`/`System.err` for diagnostics (`out`→`info`, `err`→`warn`/`error(msg, throwable)`). The SLF4J **API** is the only logging dep in library modules; the **backend** (`logback-classic`, managed at `logback.version` in the parent) lives only in the entry module `pig-agent-cli`, configured by `pig-agent-cli/src/main/resources/logback.xml` (console + rolling file → `~/.pig-agent/workspace/logs/pig-agent.log`; `io.pigagent`=INFO, noisy libs=WARN). Tests use `logback-test.xml` (WARN, console-only); the DashScope SDK's bundled `slf4j-simple` is excluded in `pig-agent-providers` to keep Logback the sole binding. **Genuinely interactive terminal I/O is NOT logging and stays on the console**: the `OnboardingWizard` prompts, the startup ASCII banner, and REPL output via `Ansi.println(terminal, …)`.

## AI 开发流水线（`/ls:*`）

> **强制规约**：实现任何需求/特性/修复 MUST 走此流水线，不得跳阶段/越人工门/自行拍板拆分。硬性规则见 [`.claude/rules/common/ls-pipeline.md`](.claude/rules/common/ls-pipeline.md)。

一条半自动的 AI 开发流水线，把既有能力串成标准流程（命令定义在 `.claude/commands/ls/`，复用 `/opsx:*` + `.claude/rules/common/`，不重造）。

```
需求澄清 → 特性分支(feat/bug/docs/opt) → spec 设计 → [编码⇄单测 内环] → 集成测试 外环 → openspec 归档
```

| 命令 | 阶段 | 门 | 职责 |
|------|------|-----|------|
| `/ls:clarify` | 需求澄清 + 拆分 + 建分支 | ⏸ 人工 | AskUserQuestion 问清需求；**大需求拆成多个可独立上线的 spec（人工审拆分）**；每个 spec 从 `origin/main` 拉 `<type>/<name>` 分支（可并行） |
| `/ls:spec` | spec 设计 | ⏸ 人工审批 | 委托 `/opsx:propose` 生成 proposal/design/tasks + delta spec，`openspec validate --strict` |
| `/ls:code` | 编码⇄单测（**内环**） | 自动 | 逐 task TDD：测试→实现→`mvn test`→勾选；组后 `mvn compile` |
| `/ls:itest` | 集成测试（**外环**） | 自动 | 跑 `*IT` 真模型测试；失败回喂 `/ls:code`；连续 3 轮无进展升级人工 |
| `/ls:archive` | openspec 归档 | ⏸ 人工确认 | 委托 `/opsx:archive`：同步主 spec + 移到 `changes/archive/` |
| `/ls:status` | 进度汇报 | 只读 | 跨 澄清/设计/规格/任务 维度统计所有活跃 spec（多 spec 并行视图 + 卡点） |
| `/ls:dev` | 总控 | 半自动 | 端到端串联五阶段，尊重上述人工门 |

**两层 loop engine**：内环 = 编码⇄单测（`/ls:code`，快、离线）；外环 = 任务→内环→集成测试（`/ls:itest`，慢、真模型），失败回环至绿。**半自动**：澄清/spec/归档人工把门，编码+测试自动推进。**多 spec**：大需求在 `/ls:clarify` 拆成多个可独立上线的 spec（拆分须人工审），各自 `feat/<name>` 分支——**依赖允许时并行，否则按依赖顺序推进**（后者在前者归档后才细化 tasks），`/ls:status` 汇总进度。**分支前缀**：`feat`/`bug`/`docs`/`opt`（`bug/` 分支的提交信息仍用 conventional-commit `fix:`）。完整指南 + 实战复盘见 `docs/ai-dev-pipeline.md`；规约基座见 `.claude/rules/common/development-workflow.md`。
